### TASK-13a — Backup SQLite (VACUUM INTO), Rotação (Frequência 6h), Permissões e Restauração

**Tipo:** infraestrutura & resiliência de dados  
**Arquivos:** `src/lib/db-backup.ts`, `package.json`, `src/test/booking-engine.test.ts`, `docs/backups.md`

**O que fazer:**
1. **Script de Snapshot Atômico Local (`src/lib/db-backup.ts`)**:
   - Destino **fora do repositório git**:
     - Variável de ambiente `SQLITE_BACKUP_DIR` ou fallback `$HOME/.backups/ink-sharp-editorial/`.
     - Permissões POSIX do diretório: aplicar `fs.chmodSync(dir, 0o700)` (`rwx------`).
   - Nome com timestamp para garantir unicidade: `leads_backup_YYYY-MM-DD_HHmmss.db`.
   - **Prevenção de erro SQLite**: Como `VACUUM INTO` falha imediatamente se o arquivo de destino já existir, verificar via `fs.existsSync(dest)` e abortar ou incrementar sufixo se necessário.
   - Execução via conexão sincronizada:
     ```ts
     const db = getDb();
     db.exec(`VACUUM INTO '${destPath}'`);
     ```
   - Permissões POSIX do arquivo gerado: aplicar `fs.chmodSync(destPath, 0o600)` (`rw-------`).
   - **Rotação Local**: Reter os **28 backups mais recentes** (equivalente a 7 dias com frequência de 4 backups diários a cada 6h) e remover os excedentes com `fs.unlinkSync`.
2. **Teste Automatizado de Restauração e Integridade**:
   - No `booking-engine.test.ts`:
     - Executar `createDatabaseBackup()`.
     - Abrir o arquivo de snapshot gerado com uma nova instância independente `const backupDb = new DatabaseSync(backupPath)`.
     - Executar `PRAGMA integrity_check;` e validar que retorna `[{ integrity_check: "ok" }]`.
     - Validar que a contagem de registros em `bookings`, `leads` e `settings` no backup é idêntica à do banco ativo.
     - Limpar os artefatos de teste temporários.
3. **Documentação de Backup e RPO em `docs/backups.md`**:
   - **Frequência e RPO Real**:
     - **Frequência**: Execução **a cada 6 horas** (`00:00`, `06:00`, `12:00`, `18:00` UTC). Como o banco SQLite é extremamente leve (poucos megabytes), o custo computacional e de I/O é praticamente nulo.
     - **RPO (Recovery Point Objective)**: **RPO máximo = 6 horas** (estritamente o intervalo entre snapshots consistentes). Não documentar fantasias de "RPO < 1h com WAL", pois sem snapshot consistente o arquivo `-wal` isolado não constitui mecanismo de recuperação suportado.
   - **Sincronização Off-Site**:
     - Documentar comando de cópia: `rclone copy $BACKUP_DIR remote:ink-sharp-backups/sqlite/`.
     - Credenciais do rclone protegidas obrigatoriamente com permissão mínima `0600` (`rw-------`).
   - **Procedimento Passo a Passo de Restauração Periódica**:
     1. Baixar snapshot íntegro do storage remoto.
     2. Validar integridade via `sqlite3 restore.db "PRAGMA integrity_check;"`.
     3. Parar serviço da aplicação (`systemctl stop ink-sharp`).
     4. Mover banco corrompido e apagar resquícios de WAL (`leads.db-wal`, `leads.db-shm`).
     5. Restaurar o arquivo na pasta `data/leads.db` com permissão `0600`.
     6. Reiniciar aplicação e validar status via health check.
   - **Piso e Configuração de Node.js**:
     - Fixar em `package.json`: `"engines": { "node": ">=22.13.0" }`.
     - Documentar que o Node 22.13.0 é a versão oficial onde o módulo `node:sqlite` dispensa flags experimentais de CLI no runtime.
     - Registrar explicitamente que `node:sqlite` emite aviso de funcionalidade experimental no runtime do Node.js, não devendo ser classificado como "estável".

### TASK-15 — Sincronização Atômica Lead ↔ Booking, Rollback via Trigger e KPIs Contábeis

**Tipo:** regra de negócio transacional & dados analíticos  
**Arquivos:** `src/server/api/bookings.ts`, `src/lib/db.ts`, `src/routes/admin.tsx`, `src/components/admin/bento-overview.tsx`, `src/test/booking-engine.test.ts`

**O que fazer:**
1. **Avanço Unidirecional do Lead (`lead_id`)**:
   - No `POST /api/bookings`, se `lead_id` for enviado:
     - **Validação com Rollback**: Verificar se o lead existe. Se `SELECT id, status FROM leads WHERE id = ?` não retornar nada, **abortar imediatamente a transação com 422** (`"Lead informado não existe"`). O booking NÃO deve ser persistido.
     - **Regra de Avanço**: Se o lead existe e seu status atual for `"novo"` ou `"contatado"`, atualizar para `"agendado"` dentro do mesmo bloco `BEGIN IMMEDIATE`:
       ```sql
       UPDATE leads SET status = 'agendado' WHERE id = ?;
       ```
     - **Regra Anti-Regressão**: Se o lead já estiver em `"agendado"` ou `"arquivado"`, o status do lead é preservado (nunca regride).
     - Gravar evento em `booking_events` com chave `"lead_linked"`.
2. **Cancelamento/No-Show Atômico com o Lead e Teste de Rollback via Trigger**:
   - Ao cancelar um booking ou marcar no-show (`PATCH /api/bookings/:id` com status `"cancelado"` ou `"no_show"`):
     - Executar a transição do booking e a atualização do lead **dentro da mesma transação `BEGIN IMMEDIATE`**.
     - Verificar se o lead possui outros bookings ativos (`status NOT IN ('cancelado', 'no_show')`):
       - Se possuir: mantém status `"agendado"`.
       - Se não possuir mais nenhum booking ativo: o lead passa para `"contatado"` (nunca regride para `"novo"`, preservando o histórico de qualificação).
   - **Teste de Rollback Obrigatório com Trigger Temporário**:
     - No teste unitário, criar trigger temporário no SQLite para simular falha determinística:
       ```sql
       CREATE TRIGGER test_fail_lead_update
       BEFORE UPDATE ON leads
       FOR EACH ROW
       BEGIN
         SELECT RAISE(ABORT, 'Simulated lead update failure for rollback test');
       END;
       ```
     - Disparar o cancelamento do booking.
     - Validar que a transação inteira sofreu `ROLLBACK`: nem o status do booking mudou para `"cancelado"`, nem o lead sofreu alteração.
     - Executar `DROP TRIGGER test_fail_lead_update;` para manter o banco limpo.
3. **Fórmulas Contábeis dos KPIs do Dashboard Bento**:
   - `BentoOverview` recebe `bookings: Booking[]` e `leads: Lead[]`.
   - **Sinais Recebidos**:
     $$\text{Sinais Recebidos} = \sum_{\text{booking} \in \text{filtrados}} \text{deposit\_cents} \quad (\text{onde } \text{deposit\_status} \in \{\text{'pago'}, \text{'retido'}\})$$
     *(Sinais retidos após cancelamento/no-show configuram receita retida do estúdio e compõem o caixa).*
   - **Receita Prevista (Potencial Ativo)**:
     $$\text{Receita Prevista} = \sum_{\text{booking} \in \text{filtrados}} \text{price\_total\_cents} \quad (\text{onde } \text{status} \notin \{\text{'cancelado'}, \text{'no\_show'}\})$$
   - **Filtro Temporal (7D, 30D, 90D)**:
     - As fronteiras do filtro temporal devem ser calculadas a partir da **meia-noite local do ateliê** (`settings.timezone`, padrão `America/Sao_Paulo`), convertida para ISO UTC semiaberto `[startUtc, endUtc)`:
       - Início: $\text{hoje} - N\text{ dias}$ às 00:00 local $\rightarrow$ UTC.
       - Término: $\text{hoje} + 1\text{ dia}$ às 00:00 local $\rightarrow$ UTC.

### TASK-17 — Migração Global `warning → warnings[]`, Precedência de Conflitos e Auditoria em `booking_events`

**Tipo:** regra de negócio, contrato de API & auditoria  
**Arquivos:** `src/lib/db.ts`, `src/server/api/bookings.ts`, `src/components/admin/calendar/BookingModal.tsx`, `src/components/admin/agenda-tab.tsx`, `src/components/admin/calendar/ConfirmDialog.tsx`, `src/test/booking-engine.test.ts`

**O que fazer:**
1. **Migração Exaustiva do Contrato `warning → warnings[]`**:
   - Atualizar **todos** os consumidores sem exceção, eliminando completamente o formato legado:
     - `src/lib/db.ts`: interface `BookingResult` e rotinas `createBooking` e `rescheduleBooking` retornam `warnings: Array<{ code: string; message: string }>`.
     - `src/server/api/bookings.ts`: payload da API retorna `warnings: Array<{ code: string; message: string }>`.
     - `src/components/admin/calendar/BookingModal.tsx`: leitura e tratamento de `res.warnings`.
     - `src/components/admin/agenda-tab.tsx` (`handleReschedule`): leitura e tratamento de `res.warnings`.
     - `src/test/booking-engine.test.ts`: asserções de testes existentes migradas de `.warning` para `.warnings`.
2. **Precedência Absoluta de Conflitos**:
   - Se houver colisão de horário (`booking_conflict` ou `time_block_conflict`):
     - A API retorna **imediatamente o status 409 Conflict sem nem sequer processar ou calcular warnings**!
     - `force: true` **NUNCA ignora ou suprime bloqueios duros (`time_block_conflict`) ou sobreposições de agendamentos (`booking_conflict`)**! O parâmetro `force: true` serve estritamente para contornar avisos operacionais acumulados (`outside_hours`, `past_date`, `future_window`).
3. **Auditoria Forense em `booking_events`**:
   - Quando um booking for criado (`POST /api/bookings`) ou remarcado (`PATCH .../reschedule`) com `force: true`:
     - Identificar quais avisos foram ignorados pelo usuário (ex.: `outside_hours`, `past_date`).
     - Gravar registro correspondente na tabela `booking_events` com chave `"created"` ou `"rescheduled"`, contendo no campo `note` ou metadata os códigos explícitos dos avisos ignorados:
       ```
       "Avisos ignorados com force: outside_hours, past_date"
       ```
     - Garante rastreabilidade total caso o tatuador queira auditar no futuro por que um agendamento foi marcado em dia de folga ou data especial.
4. **Comportamento em Reschedule / Drag & Drop**:
   - Se o reagendamento via arrasto no FullCalendar retornar `requires_force: true` com `warnings: []`:
     - O front-end intercepta a resposta e abre o `ConfirmDialog` exibindo a lista de todos os avisos acumulados.
     - Se o tatuador clicar em **Confirmar**: dispara o PATCH com `force: true`.
     - Se o tatuador clicar em **Cancelar**: invoca imediatamente `eventDropInfo.revert()` ou `eventResizeInfo.revert()`, restaurando o evento para a posição original no calendário.
