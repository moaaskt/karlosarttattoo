## Fatos do Backend (lidos das rotas e db.ts reais)

### Chaves de Resposta das Rotas GET:
- `GET /api/settings` → `{ success: true, settings: { ... } }` (chave: `settings`)
- `GET /api/availability-rules` → `{ success: true, rules: [ ... ] }` (chave: `rules`)
- `GET /api/bookings` → `{ success: true, bookings: [ ... ] }` (chave: `bookings`)
- `GET /api/time-blocks` → `{ success: true, timeBlocks: [ ... ] }` (chave: `timeBlocks`)
- Sempre setar o estado com fallback de segurança: `data.settings ?? {}`, `data.rules ?? []`, `data.bookings ?? []`, `data.timeBlocks ?? []`.

### AvailabilityRule (campos reais)
```ts
interface AvailabilityRule {
  id: string;
  day_of_week: number;   // 0=Dom … 6=Sáb
  window_start: string;  // "09:00"
  window_end:   string;  // "20:00"
  is_active:    number;  // 1 = ativa, 0 = inativa
}
```

### Settings (chaves reais — sem slot_min/max_time no banco)
| Chave | Default |
|-------|---------|
| `timezone` | `America/Sao_Paulo` |
| `buffer_minutes` | `30` |
| `preset_manha` | `09:00` |
| `preset_tarde` | `14:00` |
| `preset_noite` | `18:30` |

### Filtro de sobreposição
`listBookings` e `listTimeBlocks` usam `WHERE ? < end_at AND start_at < ?` com `params.push(from, to)`.
Semântica: `from < end_at AND start_at < to` — correto para sobreposição.
Adicionar testes de cobertura na TASK-05b respeitando o expediente ou com `force: true`.

### rescheduleBooking — respostas reais
| Condição | HTTP | Body |
|----------|------|------|
| `outside_hours` + `force=false` | 409 | `{ warning: "outside_hours", message }` — **sem booking** |
| `time_block_conflict` | 409 | `{ error: "time_block_conflict", conflicts, message }` |
| `booking_conflict` | 409 | `{ error: "booking_conflict", conflicts, message }` |
| `invalid_status` | 422 | `{ error: "invalid_status", message }` |
| Sucesso + warning | 200 | `{ success: true, booking, warning: "outside_hours" }` |
| Sucesso normal | 200 | `{ success: true, booking }` |

`force` já existe na rota e no `rescheduleBooking`.

### Toast/Diálogo disponíveis
- **`sonner@^2.0.7`** — já instalado; usar `toast.success/error/warning/info`.
- **`@radix-ui/react-dialog`** — já instalado; usar para diálogos de confirmação (reter/devolver sinal).
- **Proibido** `alert()` e `window.confirm()`.
- Garantir que `<Toaster />` esteja montado na árvore de `/admin`.

### deposit_cents vs price_total_cents — regra unificada
Invariante: `deposit_cents <= price_total_cents` **somente quando `price_total_cents > 0`**.
Se `price_total_cents === 0` (não informado), `deposit_cents` é livre (validação não falha).
Aplicar igualmente em:
1. `POST /api/bookings` (create) via Zod refine.
2. `PATCH /api/bookings/:id` (update dados) via Zod refine + verificação no db ignorando campos iguais ao atual.
3. `PATCH /api/bookings/:id/deposit` (update sinal) via verificação com o `price_total_cents` atual do booking.

## Decisões de Arquitetura

### D-A: Módulo puro `src/lib/agenda-utils.ts`
Arquivo **sem React**, sem imports de runtime de `db.ts`. Exporta:
- `bookingToEvent(b, showCancelled, interactive)` — `editable = interactive && isEditable`. Onda A passa `false`, Onda B passa `true`.
- `timeBlockToEvent` — mapeamento FullCalendar (`display: "background"`).
- `STATUS_COLOR`, `DEPOSIT_BORDER`, `SESSION_TYPE_LABEL` — constantes visuais.
- `VALID_TRANSITIONS` — máquina de estados de agendamentos.
- `deriveSlotMinTime`, `deriveSlotMaxTime` — fallback `"07:00:00"` / `"23:00:00"` sem regras ativas.
- `localToUTC(date, time, tz): string` — usa `luxon.DateTime`.
- `utcToLocal(iso, tz): { date, time }` — usa `luxon.DateTime`.
- **Import:** `import { DateTime } from "luxon"` no topo (sem `require()`).
- **Tipos:** importar via `import type { Booking, TimeBlock, AvailabilityRule } from "./db"`.

### D-B: `src/lib/api-client.ts`
Módulo cliente. Exporta:
- `toUTCString`, `centsToDisplay`, `displayToCents`, `formatWhatsAppPhone`.
- `ERROR_MESSAGES`, `getErrorMessage`.
- `apiFetch<T>` — injeta `Authorization: Bearer`, trata 401 deslogando com evento customizado.
- Não contém lógica de calendário.

### D-C: Padrão client-only (idêntico ao `ApexChartClient`)
**Sem** `next/dynamic` nem `'use client'`. `React.useState + React.useEffect + import()` dinâmico. Plugins fixados como variável estável fora do componente (evitar re-renders):
```ts
let cachedPlugins: any[] | null = null;
```

### D-D: Serialização de datas e imports de tipos
**Nunca** `startStr`/`endStr` do FullCalendar enviados para a API. Usar `event.start.toISOString()`.
Usar `import type` de `@fullcalendar/core` (`EventInput`, `DatesSetArg`, `EventContentArg`, `EventClickArg`, `EventDropArg`).
Fixar `@fullcalendar/core` e todos os plugins na mesma versão para evitar múltiplas instâncias (`npm ls @fullcalendar/core` deve mostrar uma única cópia).

### D-E: Early return e regras de hooks do React
No `AgendaTab` e outros componentes, **todos os React Hooks (`useState`, `useEffect`, `useMemo`, `useRef`) devem ser chamados antes de qualquer early return** (ex: `if (!isReady)`).

## Tasks — ONDA A

### TASK-05b — PATCH /api/bookings/:id (edição de dados) + Refine de Sinal + Testes

**Tipo:** backend  
**Arquivos:** `src/server/api/bookings.ts`, `src/lib/db.ts`, `src/test/booking-engine.test.ts`

**Endpoints & Regras:**
1. `POST /api/bookings`: Adicionar `.refine` no schema Zod para garantir que `deposit_cents <= price_total_cents` somente se `price_total_cents > 0`.
2. `PATCH /api/bookings/:id/deposit`: Adicionar verificação de que `deposit_cents <= price_total_cents` quando `price_total_cents > 0`.
3. `PATCH /api/bookings/:id` (edição de dados cadastrais/sessão):
   - Schema Zod `updateBookingDataSchema`:
     ```ts
     {
       client_name?:       z.string().trim().min(2),
       client_phone?:      z.string().regex(phoneRegex),
       client_email?:      z.string().email().nullable().or(z.literal("")),
       location?:          z.enum(["estudio","domicilio","evento"]),
       session_type?:      z.enum(["tatuagem","flash","retoque","projeto","outro"]),
       price_total_cents?: z.number().int().min(0),
       deposit_cents?:     z.number().int().min(0),
       notes?:             z.string().nullable(),
     }
     // .refine: pelo menos um campo presente
     // .refine: se price_total_cents > 0 e deposit_cents informado, deposit <= price
     ```
   - Nova função `updateBookingData(id, patch)` em `db.ts`:
     - Ignorar campos cujos valores sejam estritamente iguais aos valores atuais do booking (não lançar erro 422 por reenvio do mesmo valor).
     - Se `cancelado` ou `no_show`: recusar alteração de `client_name`, `client_phone`, `client_email` com 422 `invalid_transition`.
     - `concluido`: aceita edição de dados de contato e notas.
     - Se `notes` for alterado: gravar evento `note_updated` em `booking_events`.
     - Validação mesclada: se `price_total_cents` e/ou `deposit_cents` mudarem, verificar `deposit_final <= price_final` se `price_final > 0`.
     - Se `current.deposit_status` for `"pago"`, `"retido"` ou `"devolvido"` e `patch.deposit_cents` for enviado com valor diferente do atual: retornar 422.

**Testes `node:test` (em `booking-engine.test.ts`):**
- POST com `deposit_cents > price_total_cents` quando `price_total_cents > 0` → 422.
- POST com `deposit_cents > 0` quando `price_total_cents === 0` → passa (preço livre).
- PATCH /deposit com `deposit_cents > price_total_cents` (quando `price > 0`) → 422.
- PATCH /api/bookings/:id:
  - Editar `client_name` de booking `pendente` → sucesso.
  - Editar com o mesmo valor atual → sucesso sem 422.
  - Editar `client_name` de booking `cancelado` → 422 `invalid_transition`.
  - Editar `client_name` de booking `concluido` → sucesso.
  - Body sem campos editáveis → 422.
  - `deposit_cents > price_total_cents` (após merge) → 422.
  - `notes` alterado → evento `note_updated` em `booking_events`.
  - Cobertura de `listBookings` e `listTimeBlocks` (adjacência e sobreposição) com horários dentro do expediente ou `force: true`.
